# Contributing to Recruitify

Thank you for helping improve Recruitify. Keep changes focused, reviewable, and accompanied by the schema and tests they require.

## Branch strategy

- `main` is the stable branch and should remain deployable.
- `version2` is the active integration branch for the current development line.
- Create a short-lived feature or fix branch from `version2`, then open a pull request back to `version2`.
- Promote tested releases from `version2` to `main` through a separate pull request. Do not commit directly to `main`.

If maintainers announce a different release target, follow the pull request's stated base branch.

## Commit messages

Write imperative, scoped messages that explain the outcome, for example:

```text
Add application status validation
Document PostgreSQL migration workflow
Fix duplicate interview reminders
```

Keep unrelated refactors out of feature commits. When a model changes the schema, commit the model and its generated migration together.

## Migration workflow

Run migration commands from `backend/`:

```bash
flask --app run:app db migrate -m "describe the schema change"
# Review the generated upgrade() and downgrade().
flask --app run:app db upgrade
flask --app run:app db current
```

- Treat autogenerated migrations as drafts and inspect them before running or committing.
- Test upgrades on a disposable local database; also validate PostgreSQL-specific behavior where relevant.
- Never use `create_db.py` to update an existing database.
- Never edit or remove a migration that has been committed and shared. Add a corrective migration instead.
- Resolve multiple migration heads with a reviewed Alembic merge revision.

See the [database migration workflow](README.md#database-migration-workflow) for the complete rationale and command reference.

## Pull request workflow

1. Update your branch from its target branch and resolve conflicts locally.
2. Keep the pull request limited to one coherent change.
3. Describe the problem, solution, verification steps, and any schema or deployment impact.
4. Include screenshots for visible frontend changes and sample requests/responses for API contract changes.
5. Include model and migration files together when the database schema changes.
6. Request review only after relevant tests and local checks pass.
7. Address review feedback with additional commits; avoid rewriting shared migration history.

## Code review expectations

Reviewers should check correctness, authorization boundaries, API compatibility, migration safety, error handling, test coverage, and maintainability. Authors should respond to each substantive comment or explain the chosen tradeoff. At least one approving review is recommended before merge, with extra scrutiny for authentication, data, and deployment changes.

## Testing expectations

Run the checks relevant to your change:

```bash
# From backend/
pytest

# From frontend/
npm test
npm run build
```

Add or update tests for changed behavior. For schema changes, test the migration upgrade and assess the downgrade for data loss. Record any check that could not be run, and why, in the pull request.
